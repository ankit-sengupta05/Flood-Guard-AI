# Constraints — Flood-Guard AI (SIH 2026, PS 26161)

## 1. Project Constraints

- **C1 — Timeline:** Hackathon timeframe (~10–13 days per the phased breakdown in `PRD.md`). The system spans many independently-impressive modules (SPH, Delft3D, uncertainty, satellite validation, evacuation, priority engine, explainability, offline mode). Treat one fully-working "hero dam" end-to-end as the non-negotiable minimum before broadening to more dams or more polish.
- **C2 — Team size/specialization:** Assumes a multi-person team split roughly across data/GIS, simulation, ML/decision-logic, backend, and frontend. `api_endpoints.md` exists specifically so these sub-teams work in parallel — treat contract changes as requiring a quick sync, not a silent code change.
- **C3 — Budget:** Zero/near-zero. Every tool in `tech_stack.md` is free, open-source, or free-tier. Google Earth Engine is free for research/education use but requires account approval and quota awareness — confirm access in Phase 0/1, not later. This is also why the 3D globe/terrain stack defaults to MapLibre GL JS + self-hosted terrain-RGB tiles (free, no account) rather than Cesium ion (usage-capped free tier, real cost risk if the demo goes viral or judges leave it open) — see `tech_stack.md` §1.
- **C4 — No real dam-sensor telemetry:** This prototype does not monitor a real dam's live sensors (see the explicit non-goal in `PRD.md` §6). All source-water and breach parameters are either user-specified in the Scenario Builder or auto-generated best/likely/worst-case variants — there is no claim of continuous structural-health monitoring.
- **C5 — SPH/Delft3D are heavy, specialist tools:** Neither SPH implementations (PySPH, DualSPHysics) nor Delft3D/Delft3D-FM are designed for a hackathon's compressed setup time or typical free-tier hosting (Delft3D in particular is resource-intensive and traditionally desktop/HPC-oriented). This directly shapes C6 below.

## 2. Technical Constraints

- **C6 — Real Model Mode vs. Demo/Surrogate Mode is the central, non-negotiable distinction:** The hydrodynamic-engine adapter layer (see `architecture.md` §2.5, `tech_stack.md` §2) must make every SPH/Delft3D result carry an explicit `model_mode: "real"|"surrogate"` field, and every dashboard page showing a result must render that label. Given C1/C5, the realistic default build path is: get the full pipeline working end-to-end on **Demo/Surrogate Mode** first, then attempt a genuine SPH and/or Delft3D run for the hero dam only if time allows. It is a severe violation of the master prompt's explicit rules to present a simplified mathematical approximation as if it were a full SPH or Delft3D simulation — this must never happen, including under judge-facing time pressure.
- **C7 — SPH/Delft3D comparison and coupling must be scientifically honest:** When both engines are run, the comparison (extent, depth, velocity, arrival time, compute time) is valid whether both ran in real or surrogate mode, but the two must be run in the *same* mode for a fair comparison — comparing a real SPH run against a surrogate Delft3D run (or vice versa) is misleading and must be avoided or clearly flagged if unavoidable. The coupled workflow (SPH hydrograph → Delft3D boundary) is a simplification even in "real" mode — document the exact coupling variable and conversion step used (per FR4.3), rather than asserting a fully rigorous multi-physics coupling.
- **C8 — 3D/2D playback is precomputed, not live physics:** Timestep scrubbing on the Flood Map, SPH Simulation, and Delft3D Simulation pages plays back precomputed grids; the simulation itself runs once per triggered scenario (seconds to minutes depending on mode), not per frame in the browser. This is the correct, industry-standard approach — state it as such rather than as a limitation.
- **C9 — Uncertainty quantification is a prototype-level approximation:** The Uncertainty Engine runs an ensemble across a bounded fallback range and aggregates into probability/confidence labels; this is not a full stochastic-hydrology or Monte-Carlo-calibrated treatment. State this plainly on the Assumptions and Data Quality page (per FR5.3) rather than implying a rigorously calibrated probability.
- **C10 — Satellite validation depends on scenario/event alignment:** IoU and agreement-percentage validation (FR9) are only meaningful when the scenario corresponds to a real historical event with available cloud-free Sentinel/Landsat imagery for that window. For a purely hypothetical "what-if" scenario (e.g. a judge-selected water level/breach combination with no real-world counterpart), there is no observed extent to validate against — the Satellite Validation page must show this as an explicit "no matching observation available" state, not a fabricated or zero-value comparison.
- **C11 — Forecast updating is a simplified mechanism, not full data assimilation:** FR10's forecast-updating feature folds a new observation into a re-run or reweighted scenario; it is not a Kalman-filter-grade or ensemble-data-assimilation system. State this distinction wherever the feature is shown or discussed with judges.
- **C12 — Evacuation routing uses real road-network topology but simulated flood/closure data:** `osmnx`-sourced road networks are real; which segments are "unsafe" at a given time comes from the Hydrodynamic Engine's output for a scenario (real or surrogate), not observed real-world closures. The routing algorithm itself (time-aware shortest path avoiding unsafe segments) is sound engineering regardless of which mode produced the underlying flood data.
- **C13 — Population, vulnerable-group, and shelter-capacity data will be incomplete for most demo regions:** Where such data isn't available for a given village/shelter, the Emergency Priority Engine and Smart Evacuation Engine must degrade gracefully (omit or down-weight the missing factor and note it, per the Missing-Data Diagnostic Engine's general pattern) rather than fabricating population or capacity figures.
- **C14 — Terrain/coordinate consistency per dam:** Each registered dam needs one consistent coordinate reference system across its DEM, river network, and village/road/building layers, matching the bounding boxes in `important-dam-locations.md`. Do not mix data sourced at different resolutions/projections for the same dam without reprojecting first.
- **C15 — Offline mode is browser-cache-based, not a native offline app:** The pre-download/offline-viewing/offline-report-generation feature (FR11) is implemented via service worker + IndexedDB within the responsive web app, not a separate mobile application — state this scope boundary if asked.

## 3. Security & Access Constraints

- **C16 — Role/permission enforcement is server-side only:** The frontend may hide UI elements based on role, but every sensitive endpoint (per `api_endpoints.md`'s permission matrix) independently verifies the requester's role/scope server-side. A hidden button is not a security boundary.
- **C17 — Scoped access, not just role-based:** `ANALYST` and `EMERGENCY_MANAGER` are scoped to specific `dam_ids`/`district_ids`, not globally permissive within their role tier. Checked on every request touching a specific dam's data, not just at login.
- **C18 — Evacuation-plan overrides and dam-metadata edits need an approval trail:** Per FR-level rules in `PRD.md`/`api_endpoints.md`, `ANALYST`-proposed overrides require `EMERGENCY_MANAGER`/`SYSTEM_ADMIN` approval before taking effect, with a minimal audit trail (who proposed, who approved, when) — also a useful demo talking point on system trustworthiness.

## 4. Data & Validation Constraints

- **C19 — No real historical dam-failure ground truth for calibration:** Neither the SPH/Delft3D parameterization nor the priority-scoring weights are fitted against real Indian dam-failure outcomes; they rely on established engineering approximations, published breach-parameter regressions (e.g., Froehlich-style relationships where used), and domain-literature heuristics. This is standard practice in this domain for a prototype and should be presented as such, not overclaimed as validated.
- **C20 — Empirical equations and heuristics as ground-truth proxies:** Where a full physics run isn't performed (surrogate mode), the approximation should be based on a defensible, briefly-documented method (e.g., a simplified shallow-water/kinematic-wave approximation), not an arbitrary interpolation — so that even the "fake" numbers are a reasonable order-of-magnitude stand-in, per the master prompt's instruction to avoid scientifically false claims even in a simplified prototype.
- **C21 — Village/building representation:** Villages/buildings are represented as points or simple polygons from open datasets (e.g., OSM), not detailed building-footprint data, unless a specific open dataset for the demo region provides this cheaply.
- **C22 — 3D-only visualization, no 2D map fallback:** Every map/scene surface in the product (Home/Command Center globe and all 13 map-bearing dashboard pages) is rendered as a real 3D environment (`tech_stack.md` §1–2, `design-system.md` §6) — there is no flat 2D Leaflet-style map anywhere, including for pages that would be simpler as one. This raises the browser/GPU bar (WebGL required; low-end devices may need a reduced-detail terrain LOD) and adds one real preprocessing step per dam (DEM → glTF terrain mesh + terrain-RGB tiles, `tech_stack.md` §1), which — like timestep grids (C8) — must be generated once per dam ahead of time, never meshed live per request.
- **C23 — Drone free-fly view is a camera mode, not a new simulation:** The free-fly "drone view" camera (WASD/mouse-look navigation through the 3D scene) only changes *how* already-computed depth/velocity/arrival-time grids and the precomputed terrain mesh are viewed. It never triggers a new physics run, never computes flood behavior client-side, and is available identically in Real Model Mode and Demo/Surrogate Mode — the `model_mode` label (C6) still applies to whatever data the drone camera is currently flying through.

## 5. Assumptions Requiring Early Decisions

Lock these down in Phase 0/1 and avoid revisiting mid-build:

- **A1:** Hero dam selection and 2–4 additional lighter-data dams to populate the map (see `important-dam-locations.md` for candidates and DEM bounding boxes).
- **A2:** Real Model Mode ambition level — recommended default: build the full pipeline in Surrogate Mode first; attempt a genuine SPH and/or Delft3D run only for the hero dam, only if time allows after Phase 5.
- **A3:** Whether the hero-dam scenario corresponds to a real historical event (enabling genuine satellite validation) or a purely hypothetical judge-selected scenario (in which case Satellite Validation demos the workflow using the nearest available real-event proxy, clearly labeled as such).
- **A4:** Source of road-network data for evacuation routing (recommended: `osmnx`/OpenStreetMap for the demo region).
- **A5:** Whether the conversational scenario assistant (FR15.2) is built at all for the hackathon — recommended: build only if the retrieval-grounding (no hallucinated numbers) can be reliably demonstrated; otherwise ship the Explainability page (18, `frontend_spec.md`) without the free-form query box.
- **A6:** Population/vulnerable-group/shelter-capacity data source and how gaps are handled for the demo region (per C13).

## 6. Known Limitations to State Upfront (in report/pitch)

- SPH and Delft3D results are Demo/Surrogate Mode by default for most scenarios; a genuine physics run, where attempted, is clearly labeled and scoped to the hero dam only (C5, C6).
- Uncertainty quantification is ensemble-based and prototype-level, not a fully calibrated stochastic treatment (C9).
- Satellite validation is only meaningful where a real-event time window with usable imagery exists; hypothetical scenarios show a "no matching observation" state rather than a fabricated comparison (C10).
- Forecast updating is a simplified re-run/reweighting mechanism, not full data assimilation (C11).
- Evacuation routing uses real road-network topology but simulated flood-closure data (C12).
- Population, vulnerable-group, and shelter-capacity figures are only as complete as available open data for the demo region, and gaps are surfaced rather than silently filled (C13).
- The 3D terrain/flood scenes are real DEM- and grid-derived, but the mesh is a simplified/decimated representation of the raw DEM (not full survey-grade fidelity), and is precomputed per registered dam rather than generated live (C22).
- These are standard, deliberate scoping decisions for a system of this ambition built in a hackathon timeframe, and are worth framing exactly that way to judges — as evidence of good engineering judgment and scientific honesty (per the master prompt's explicit rule against false claims), not as hidden shortcomings.
